# ADR-0007 重繪邊界、捲動與導覽

## 狀態

已採用。

## 決策

SwiftUI 的效能問題都來自「誰訂閱了什麼」，所以每個區塊的訂閱邊界是設計的一部分：

- 只有顯示時間的元件訂閱 progress（時間文字、細進度條、進度圓點）。控制列其餘部分（標題、按鈕、Menu）不必每個 tick 重建。
- `WatchView` 的章節卡片只在「換章節」時重繪。整頁訂閱 progress 會讓正在捲動的頁面持續重排版，看起來一直在抖。
- 換頁或關掉播放頁時要解除捲動凍結，否則進度條一直停住。
- 捲動時凍結播放進度通知：捲動是主執行緒最敏感的時刻，這一秒的數字沒人看得到。留言載入用「階段變化」而不是每幀的幾何回呼：幾何版每次捲動都會跨橋進 JS，階段版一個手勢只回呼一兩次。
- 頻道頁只訂閱位移，轉成布林後用 ref 去重。SwiftUI 每幀都回呼，但只有跨過門檻才重繪。
- 拖曳中的 `PlayerHost` 每幀重繪；播放頁自己接 store，不必跟著重建。
- `WatchView` 內容跟著播放器常駐（`useMemo` 包住），換片不會重建，所以換片時要自己把分頁與捲動位置收回頂部。
- 推入頁一律用系統導覽列：邊緣返回、標題截斷、捲動材質都靠它，自己畫標頭拿不到這些。導覽列標題跟頻道名走：名字還在畫面上就不顯示，捲出去才浮出來。
- 搜尋分頁的「展開」由系統回報；不要自己設 false（會取消分頁）。
- 留言列表不用 `LazyVStack`：追加留言後它會用估算行高重算，往回捲時位置會飄、甚至到不了頂。一次一頁 20 筆、列數有限，`VStack` 的每列高度都是真的。
- 也因為 `VStack` 會一次建完，footer 一掛就會 `onAppear`，自動載入會一路連抓到底；只留明確的「載入更多」。
- 請求縮圖尺寸而不是原圖：捲動中每張都解一張 1920×1080 是最貴的一項。16:9 底板負責版面，scale-to-fill 的圖掛在 overlay，不會把卡片撐開。不是 16:9 的縮圖（例如 4:3 的 hqdefault）填滿後會比卡片高，所以圖掛在標籤層的 background。
- 小圖示畫多大隨人，吃點擊的一律 44×44（HIG 最小值），64pt 以下放大到 44pt 的觸控框，視覺尺寸不變。
- 網速掛在轉圈正下方，用 offset 不佔版面，控制列開著或收著都對得齊。
- `TabStack` 的每一頁各自被 host，stack 自己的安全區傳不進去，所以每頁根層要自己補。迷你播放器與 overlay 不能撐開分頁尺寸：畫面大小的播放器在鍵盤縮小根層時會溢出，置中的根層會把每個分頁往上推。
- 從播放器返回時先收成迷你播放器，頻道頁會開在下面的分頁上。
- 底部列是「進度條＋全螢幕」，進度條吃掉剩下的寬；直播沒有進度條，靠其他元素撐開版面。
- 時間／章節那行是唯讀文字：點它只切換控制列，不參與雙擊跳轉，也不會讓後續點擊接成雙擊。直播雙擊只當普通點擊。
- 隱藏或顯示控制列都當下反應，不排延遲。

## 後果

畫面穩定、捲動不掉幀。代價是每個新元件都要先想「它訂閱了什麼」，而不是預設接 store。
