# ADR-0006 本機儲存與資料模型

## 狀態

已採用。

## 決策

### 快取

`services/storage.ts` 把 `subscriptions`、`history` 等 key 的內容留在模組層。`Storage.get` 是原生呼叫，每次都要反序列化，而首頁每張卡片都會問一次播放位置。寫入一律走 `save*`，快取同步換掉，讀到的值唯讀。

觀看紀錄的索引與快取一起重算：紀錄最多 300 筆，寫入遠比讀取少。同 id 只留最新一筆（清單已照時間排序），對齊原本 `find` 第一個命中的行為。

首頁只在順序或進度條跨過 5% 時重繪；播放中每幾秒存一次進度。看到 90% 就算看完，不再放進「繼續觀看」。

### 跨平台模型

`services/index.ts` 是唯一知道 provider 差異的層，UI 只認 `Provider` 與統一模型。

- 排序交給 provider（bili 用 `order`、YouTube 用 chip token），不在地端排序。
- 頻道影片清單本來不帶作者，用目前頻道的資料補上。
- 詳情與串流解析會同時要同一支影片，`/x/web-interface/view` 有短期快取，共用同一個 promise 少一次往返。

### 顯示規則

- 直播沒有累計觀看數，只有當下線上人數；拿不到就不寫，別顯示 0。會員專屬影片 YouTube 不提供觀看數，同理。
- 頻道只顯示總數；抓不到就不寫，不要拿已載入數量充當總數。
- 設定值可能早於選項清單，載入時對到最接近的選項，picker 永遠有選取。
- SponsorBlock 全部分類都取消 = 不想跳任何東西，不是「用預設值」。
- 訂閱頁跨頻道聚合：全部影片都有 `publishedAt` 時依時間新到舊；否則保持「各頻道第 1 部 → 各頻道第 2 部」的交錯，避免單一頻道洗版。
- 訂閱頁快取只用來避免切換篩選時重複請求，強制重抓由 `refresh()` 清空快取觸發；沒有任何成功結果時不改動狀態，避免快取身分變動造成無限重抓。

## 後果

UI 不必知道來源差異，快取由寫入路徑維護。代價是模組層快取與 store 的狀態是兩份記憶體，任何繞過 `save*` 的寫入都會讀到舊值。
