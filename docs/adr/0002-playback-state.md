# ADR-0002 播放狀態：通知粒度、去重與換片保護

## 狀態

已採用。

## 決策

`state/playerStore.ts` 是全 App 唯一的播放狀態對外門面（實作依職責拆在 `state/player/`），訂閱分成三組，並提供 `usePlayerSelector` 讓元件只訂閱實際讀取的欄位：

- **storeState**：換片、載入、錯誤這類低頻狀態；透過 `usePlayerSelector` 做欄位級淺比較，避免無關狀態變更觸發整頁重繪。
- **progress**：每 250ms 一次的事件只以 1 秒為粒度往外送。畫面上看得到的最小單位就是秒（時間文字、進度條位置），每秒 4 次是白重畫。暫停與拖曳時完全不通知；恢復時補送最新值，進度條不會停在凍結那一刻。
- **liveViewers**：直播人數每分鐘才變一次。獨立一組訂閱，只有顯示人數的元件會收到通知。

其他規則：

- `next` 與 `storeState` 必須是不同物件。`storeState` 之後會被就地改寫，拿它當比較基準就永遠比對不到差異。
- 很多欄位（彈幕數、供應片段）會在每個 timeupdate 被重寫成同一個值；相同就不通知。
- 單一訂閱者出錯不影響其他訂閱者（見 issue-001）。
- 換片期間（上一支還在播 → 新串流 `open()` 完成）控制器吐出的事件都屬於舊片。要全部擋掉，否則會把舊片位置寫成新片紀錄，狀態也會蓋掉 loading。換流前先暫停，畫面留在最後一幀。
- 舊片剛好播完時不能把新片的 loading 蓋成 ended；最後一次 progress 要補到滿格，進度條才像「播完了」。播完不收控制列，收掉只剩定格，看起來像卡住；重播後才恢復自動隱藏。
- 直播沒有時間軸：不存位置（存了下次會拿去 seek，然後報錯）、不顯示時長、不能拖、不拉一般留言，聊天室另走 `LiveChat`。
- seek 失敗就從頭播；被後續 seek 取代的請求靜默丟棄。
- 重開串流（切畫質、換分 P、換引擎、重試）後 `open()` 會清掉控制器自己的字幕與彈幕設定，必須用 `restoreControllerSettings()` 再套一次，否則 store 顯示「已開啟」但實際沒有。
- 新 manifest 沒有某條字幕時要收掉開關，不留一個開不了的選項。換分 P 不沿用上一 P 的片段、跳過紀錄與字幕。
- 迷你播放器只是監視窗：收合時關掉字幕與彈幕，展開再依原本的選擇還原。
- 子母畫面只有 native（自訂解碼）後端支援；system（HLS）一律 `possible=false`。播放中退到背景才自動接 PiP，暫停、收掉或後端不支援就不搶；鎖屏時系統不給開，失敗靜默。
- 進過背景後，播放器的串流連線可能已失效；回來後第一次播放錯誤不顯示錯誤畫面，改走 `retryPlayback()` 在原位置重開，出現 playing 即解除。
- 播完後這顆按鈕的行為是重播，圖示要跟著說。
- 重試要重開使用者選的那個畫質，不能默默換回預設。
- 開片流程的等待點要能被打斷：`openRequestSeq` 遞增後，還在跑的流程停在下一個檢查點；停串流前先放掉預抓，播放器正在等的代理請求才會立刻失敗返回。
- 詳情、留言、SponsorBlock 並行抓，開片不等它們。字幕不擋第一幀。
- 續播點在開片前就知道，先把那一帶的片段抓起來（見 ADR-0005）。

## 後果

重繪邊界由 store 決定，UI 端只要不亂訂閱就不會發抖。代價是「哪些事件屬於哪一片」必須在 store 判斷，不能在 UI 補救。
